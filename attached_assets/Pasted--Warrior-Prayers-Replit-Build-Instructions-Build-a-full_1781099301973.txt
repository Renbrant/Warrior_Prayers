# Warrior Prayers — Replit Build Instructions

Build a full-stack responsive web application called **Warrior Prayers**.

This app is for private prayer groups where users can create invitation-only groups, share confidential prayer requests, pray through active requests, track updates, and record answered prayers.

The app must be built inside **Replit** as a complete MVP.

Before coding, create a short implementation plan, confirm the proposed stack, and list the database schema.

Do not build everything at once. Build this application in phases to reduce errors.

---

# 1. Platform Requirement

Build this application entirely inside Replit.

Use Replit as the main platform for:

* AI-assisted development
* frontend
* backend
* database
* authentication
* environment variables
* testing
* deployment

Avoid depending on external platforms unless absolutely necessary.

Use Replit’s built-in capabilities where possible.

If a feature is not natively supported by Replit, implement it with standard open-source libraries.

---

# 2. Recommended Stack

Use this stack unless Replit has a better native recommendation:

* Frontend: React
* Styling: Tailwind CSS
* Backend: Node.js with Express
* Database: Replit managed SQL database or PostgreSQL-compatible database available in Replit
* Authentication: Replit Auth where possible
* Internationalization: i18next or a simple translation dictionary structure
* Encryption: server-side encryption for sensitive fields using environment secrets
* Deployment: Replit Deployments

The code must be organized, readable, and easy to maintain.

Use clear folder structure:

* `/client`
* `/server`
* `/shared`
* `/database`
* `/utils`
* `/i18n`
* `/components`
* `/pages`

---

# 3. Development Strategy

Build the app in phases.

Do not attempt to implement the entire final app in one single coding pass.

Follow this sequence:

1. Foundation
2. Authentication and user profile
3. Private prayer groups
4. Group invitations and roles
5. Prayer requests
6. Privacy and encryption
7. Prayer Mode
8. Internationalization
9. Responsive mobile-first design polish
10. Security review

At the end of each phase, make sure the app still runs without errors.

# 8. Authentication Requirements

Users must be authenticated before accessing any internal area.

Unauthenticated users must not access:

* Prayer groups
* Prayer requests
* Prayer sessions
* Group members
* Comments
* Updates
* Invitations
* Settings

Support these login methods:

* Email and password
* Sign in with Google
* Sign in with Apple, if supported
* Sign in with Facebook, if feasible

Use Replit Auth where possible.

If Apple or Facebook login is not natively supported or would slow down the MVP, implement the authentication architecture so these providers can be added later. Do not block the MVP because of Apple or Facebook login.

At minimum, the MVP must support:

* Email/password login
* Google login, if available in Replit Auth
* Protected routes
* Logout
* Password recovery if email/password auth supports it

Avoid duplicate accounts.

If the same email logs in through different providers, link the provider or ask for secure account linking.

# 10. Core Privacy Principle

This application handles sensitive personal information.

The highest priority is protecting prayer request confidentiality.

Do not create public pages showing prayer requests.

Do not allow public group search.

Do not allow access without authentication.

Do not allow access to a group without invitation.

Do not allow one group’s data to leak into another group.

Do not reveal hidden names in summaries, reports, notifications, Prayer Mode, or history.

Do not reveal anonymous authors to regular members.

All backend routes must validate user permissions.

Frontend hiding is not enough.

---

# 11. Data Storage and Encryption

Use a centralized database for:

* Users
* Groups
* Memberships
* Invitations
* Roles
* Prayer request metadata
* Status
* Categories
* Prayer sessions
* Notifications
* Audit logs

However, sensitive prayer content must not be stored in readable plain text.

Encrypt sensitive fields before storing them.

Sensitive fields include:

* Prayer request description
* Name of the person receiving prayer
* Comments
* Updates
* Testimonies
* Closing notes
* Private notes

Use server-side encryption for the MVP using an environment secret.

Store the encryption secret in Replit Secrets or environment variables.

Do not hardcode encryption keys.

If possible, structure the code so group-based encryption can be added later.

The preferred MVP architecture is:

**Centralized database + encrypted sensitive fields + strict group access control + optional encrypted local cache later.**

Do not use local-only browser storage as the primary source of truth.

Local storage may be used only as cache or temporary draft storage.

# 13. Group Access Rules

Each group is private.

No user can search public groups.

No user can join a group without an invitation.

No prayer request can be accessed by users outside the group.

Every group-related backend route must validate:

1. User is authenticated.
2. User is an active group member.
3. User has the required role or permission.

Even if a user manually enters another group or prayer request URL, the backend must deny access unless the user is an active member of that group.

# 17. Prayer Request Privacy Rules

Create a separate field:

**Name of the person receiving prayer**

This field must be encrypted in the database.

Also store initials separately for privacy display.

If group setting `hide_prayer_person_names` is enabled:

* Display only initials everywhere.
* Do not display the full name in lists, details, Prayer Mode, notifications, history, or summaries.

Examples:

* Maria Oliveira Santos → M.O.S.
* John Smith → J.S.
* Ana Clara → A.C.
* John → J.

The request description must not be automatically modified.

Always recommend that users place names only in the dedicated name field.

# 21. Compact Prayer

Compact Prayer generates a summarized prayer guide based on all active and follow-up requests.

Compact Prayer must group requests by category.

For each category, show:

* Category name
* Number of active/follow-up requests
* Number of urgent requests
* Number of important requests
* Names or initials of people receiving prayer, based on group privacy setting
* Short generalized prayer focus
* Urgent requests highlighted separately

Compact Prayer must avoid excessive individual details.

It should be a prayer guide, not a full report.

Example:

**Health — 6 requests**

Pray for: J.S., Maria, A.C., R.P., D.M., and one anonymous request.

Summary:

Pray for healing, strength during medical treatment, wisdom for doctors, peace for families, and full recovery.

Urgent:

* J.S. has an urgent health-related request.
* One anonymous request is marked as urgent.

If names are hidden, show only initials.

Do not reveal anonymous request authors.

Do not expose unnecessary sensitive details.

---

# 22. Detailed Prayer

Detailed Prayer generates a full prayer guide.

For each request, include:

* Prayer person name or initials
* Request title
* Category
* Urgency
* Description
* Latest updates
* Important date, if available
* Suggested prayer focus
* Number of people praying
* Status
* Date created

The suggested prayer focus should be generated only from provided request details.

Do not invent facts.

Example request:

**Pray for John’s surgery on Friday.**

Suggested prayer focus:

**Pray for peace before the surgery, wisdom for the medical team, protection during the procedure, and a smooth recovery.**

Do not invent medical details, family details, or outcomes.

For each prayer request in Detailed Prayer, allow:

**Mark as Prayed**

This is different from **I am praying**.

# 29. Business Rules

1. Unauthenticated users cannot access internal areas.
2. Users only see groups where they are active members.
3. Users only see requests from groups where they are active members.
4. Users can only create requests inside groups where they are members.
5. Users can only invite members if they are admins or authorized moderators.
6. Only admins can remove members by default.
7. Only admins can change group settings.
8. The group creator cannot be removed unless primary administration is transferred.
9. Names of people receiving prayer must respect the group privacy setting.
10. Descriptions must not be used for automatic name hiding.
11. Anonymous requests must hide the author from regular members.
12. Closed requests must leave the active list and move to history.
13. Archived requests must be hidden from the main list.
14. Custom categories are specific to each group.
15. All permissions must be enforced on the backend.
16. Prayer Mode must never include requests the user cannot access.
17. Compact Prayer must not leak hidden names or unnecessary sensitive details.
18. Detailed Prayer must respect anonymous authorship and hidden names.
19. Closed requests must require a closure reason.
20. Users must be able to change their preferred language.
